# 代码版 vs Dify 版：实测对比

- 样本：`samples/conversations.json`，8 段自编对话。c07 没有我方回复，两版都直接跳过、不调模型。
- 模型：deepseek-flash，关闭思考，temperature 0.4，JSON 模式。
- 环境：2026-11-10，本机 Docker，Dify 1.19.0 自部署，从宿主机经 `http://127.0.0.1/v1` 调用。
- 汇总：`python tools/compare_runs.py code="out/code-rerun*.jsonl" dify="out/dify-rerun*.jsonl"`

## 同一时段交替各跑 3 轮（16:59–17:01，每轮 7 次模型调用）

| 指标 | 代码版 | Dify 版 |
|---|---|---|
| 状态 | ok×21，skipped×3 | ok×21，skipped×3 |
| 平均 token/次 | 2573 | 2572 |
| 端到端耗时中位数 | 2453 ms | 2174 ms |
| 端到端耗时平均 | 2906 ms（含一次 15.9 s 的接口波动） | 2452 ms |
| Dify 自报的运行耗时（平均） | - | 2401 ms |
| 重试 | 0 | 0 |

- 两版的延迟差在模型接口自身的波动范围内，看不出谁更快。
- Dify 在工作流之外的开销只有几十毫秒：不调模型的 c07 在 Dify 里跑完一次约 0.2 秒。
- 修复前 Dify 版每次 3120 token：DeepSeek 插件不支持原生结构化输出，Dify 改用提示词注入 schema。改成 JSON 模式、长度由校验节点兜底后，与代码版一致。

## 更正：之前的"Dify 每次多约 2 秒"是测量地址造成的

之前从宿主机经 `http://localhost/v1` 调 Dify，每次都多约 2 秒，曾记作平台固定开销。实际原因是：这台 Windows 上 `localhost` 先解析成 IPv6 的 `::1`，而 Dify 的端口只绑在 IPv4 的 127.0.0.1（`docker-compose.override.yaml`），连接 `::1` 被拒后 Windows 要重试约 2 秒才退回 127.0.0.1。

用 c07 两种模式各测 3 次：

| 访问地址 | 端到端 | Dify 自报的运行耗时 |
|---|---|---|
| `http://localhost/v1` | 2228–2296 ms | 151–167 ms |
| `http://127.0.0.1/v1` | 197–322 ms | 156–202 ms |

- 发现经过：先按 15 分钟时限查了 Dify 的 GitHub issues，没有一致的报告；随后 n8n 在 Docker 网络里直接调 Dify 时没有这 2 秒，对照实验确认是地址问题。
- 影响：`out/dify-run*.jsonl`、`out/dify-fix*.jsonl` 的端到端耗时都多算了约 2 秒；token、评分结果和 Dify 自报的运行耗时不受影响。`.env.example` 已改为 127.0.0.1 并注明原因。
- 复测：`python tools/overhead_probe.py samples/conversations.json 3`（环境变量 `DIFY_BASE_URL`、`DIFY_API_KEY`，换成 localhost 可复现那 2 秒）。

## n8n：评分之外的自动化

代码版只有评分内核（命令行，JSON 进、JSONL 出）。平台版的评分在 Dify，外面一圈交给 n8n：收对话、去重、调 Dify、写飞书多维表格、每日汇总、出错提醒。3 个业务工作流共 36 个节点，另有初始化、清空数据表两个维护用的小工作流，部署和运维见 `docs/n8n.md`。

平台省事的地方：

- 触发：webhook 和定时各一个节点，不用自己写服务和调度。
- 去重：用 n8n 自带的数据表记已处理的对话，一个「行不存在才放行」节点就能挡掉重复，不用另起数据库。
- 失败处理：HTTP 节点自带重试；单条失败走「错误输出」分到另一条线，不影响同批其它对话；工作流设置里指定出错工作流，没接住的失败也会记表、推送到群。
- 密钥：Dify 密钥和飞书 App Secret 存在 n8n 凭据里，执行记录里会打码，导出的工作流文件不含密钥。

画布表达不了、要绕一下的地方：

- 数据整形还得写代码：拼评分卡字段、算每日汇总、整理失败原因，7 个 Code 节点共 137 行 JS（不含空行和注释）。
- 自带的去重节点（Remove Duplicates）在当次执行就把对话记成"见过"，后面写表失败也不会再试；改成写表成功后才往数据表里记。
- 收件箱为空时，读文件节点直接报错，每 30 分钟算一次失败；要用错误输出加一个判断，把"没有文件"和真正的读文件错误分开。
- 错误输出的数据形状不统一：整个节点失败时 `error` 是字符串，HTTP 失败时是对象加 `details`，还会混进上一步的字段（比如换令牌成功留下的 `code: 0`），判断失败原因要先看 `error` 再看 `code`。
- 飞书的业务报错可能是 HTTP 200、`code` 不为 0，HTTP 节点不会当成失败；写飞书的节点后面都要加一步检查。
- n8n 凭据只能把密钥放进请求头、请求体或查询参数，不能放进 URL。群自定义机器人的密钥就在 webhook 地址里，只能明文写进节点；最后改用飞书应用机器人发消息，复用已有的应用凭据。
- 命令行 `n8n execute` 在这个版本加载不了数据表模块，初始化数据表只能临时发布一个工作流、调一次 webhook 再撤下（`tools/n8n_deploy.py --setup-tables`）。

耗时（实测）：

| 场景（2026-11-10，n8n 执行记录） | 耗时 |
|---|---|
| webhook 收到 2 段对话，评分后写进飞书 | 6.6 s |
| 定时读收件箱：3 段新对话评分后写进飞书，另 1 段去重跳过 | 9.1 s |
| 每日汇总：查表、算汇总、写表、存 Markdown、推送到群（手动 / 定时） | 7.2 s / 6.0 s |
| 收件箱里放一个写了一半的 JSON：定时任务失败，出错流程记表并推送到群 | 0.1 s 失败，出错流程 2.4 s |

- 评分耗时取决于 Dify 和模型，同上表；n8n 在 Docker 网络里直接调 Dify，没有宿主机 localhost 那 2 秒。
- n8n 不调模型，token 与 Dify 版相同；n8n 用社区版自部署。
